# ГЛАВНАЯ ЦЕЛЬ

В проекте сейчас находятся **два сайта**:

1. Старый сайт.
   - содержит накопившиеся проблемы;
   - может лагать;
   - содержит старые решения;
   - возможно содержит дублирующийся, устаревший или неиспользуемый код;
   - нужен в основном как источник логики, дизайна, функций и информации для анализа.

2. Новый сайт.
   - должен стать основной версией;
   - должен сохранить узнаваемый общий визуальный образ старого проекта;
   - при этом должен быть значительно улучшен по:
     - UI;
     - UX;
     - адаптивности;
     - скорости;
     - архитектуре;
     - стабильности;
     - безопасности;
     - SEO;
     - доступности;
     - удобству дальнейшей разработки;
     - удобству управления через админ-панель.

Новый сайт не должен выглядеть как совершенно другой бренд.

Нужно сохранить визуальную ДНК проекта, но сделать её **современной, аккуратной, дорогой, быстрой и последовательной**.

# КРИТИЧЕСКОЕ ПРАВИЛО №2 — НИЧЕГО НЕ УДАЛЯТЬ ВСЛЕПУЮ

До удаления любого файла, функции, компонента, зависимости или папки сначала определить:

1. используется ли объект;
2. где он используется;
3. для чего он был создан;
4. является ли он частью старого сайта;
5. является ли он частью нового сайта;
6. нужен ли он для миграции;
7. есть ли функциональный аналог;
8. не вызывается ли он динамически;
9. не зависит ли от него build/deploy/API/database.

Если назначение неясно:

**НЕ УДАЛЯТЬ.**

Пометить в плане:

`REVIEW_REQUIRED`

и отдельно описать, что необходимо проверить.

# ШАГ 2 — РАЗДЕЛИТЬ СТАРЫЙ И НОВЫЙ САЙТ

Это один из первых этапов будущей реализации.

Проект должен получить понятную структуру примерно такого типа:

project/
├── old-site/
│   └── ...
│
├── new-site/
│   └── ...
│
└── shared/ или infrastructure/
    └── только если это действительно необходимо

Но:

**НЕ ПРИМЕНЯЙ ЭТУ СТРУКТУРУ МЕХАНИЧЕСКИ.**

Сначала изучи текущую архитектуру и предложи структуру, которая лучше подходит именно этому проекту.

Главные требования:

- старый сайт физически отделён от нового;
- старый код больше не перемешан с новой версией;
- понятно, где находится production-сайт;
- старый сайт можно сохранить как reference/archive;
- сборка нового сайта не тащит старый код без необходимости;
- зависимости двух сайтов не конфликтуют;
- deploy нового сайта не зависит от старого;
- случайное изменение старого сайта не ломает новый.

Низкий:

- [ ] Запустить typecheck.

- [ ] Запустить lint.
- [ ] Исправить новые lint errors.
- [ ] Запустить production build.
- [ ] Убедиться, что build завершился успешно.
- [ ] Проверить изменённые страницы вручную.
- [ ] Проверить desktop.
- [ ] Проверить mobile.
- [ ] Проверить browser console.

# ПРАВИЛО ДЛЯ LUNA/TERRA

План должен быть разбит на маленькие задачи.

Одна задача должна представлять **одно проверяемое действие**.

Не объединяй в один checkbox десять изменений.

Плохо:

`- [ ] Переписать каталог, корзину, checkout, админку и базу.`

Хорошо:

- [ ] Найти текущую реализацию каталога.
- [ ] Зафиксировать используемые источники данных каталога.
- [ ] Зафиксировать текущие фильтры каталога.
- [ ] Проверить серверную и клиентскую часть фильтрации.
- [ ] Создать план новой архитектуры каталога.
- [ ] Реализовать новую архитектуру каталога.
- [ ] Проверить каталог на desktop.
- [ ] Проверить каталог на mobile.
- [ ] Проверить каталог при пустом результате.
- [ ] Проверить каталог при ошибке API.

# ЗАВИСИМОСТИ МЕЖДУ ЗАДАЧАМИ

Если задача зависит от предыдущей, явно это указывать:

`Depends on: 2.3, 2.4`

Если задачу нельзя безопасно выполнять параллельно с другой, указать:

`Do not run in parallel with: ...`

Это особенно важно для:

- database migrations;
- перемещения файлов;
- изменения auth;
- удаления зависимостей;
- изменения shared types;
- изменения API;
- изменения schema.

# SAFETY

Перед крупными изменениями предусмотреть сохранение рабочего состояния проекта.

План должен исключать ситуацию:

1. переместили 300 файлов;
2. build сломался;
3. ещё изменили database;
4. ещё переписали auth;
5. после этого начали искать источник проблемы.

Работать небольшими атомарными этапами.

После критических этапов:

CHANGE → CHECK → BUILD → TEST → CONTINUE.

# ВАЖНО: НЕ ПЕРЕПИСЫВАТЬ РАБОЧЕЕ БЕЗ ПРИЧИНЫ

Если существующий код:

- работает;
- безопасен;
- понятен;
- достаточно быстр;
- хорошо вписывается в новую архитектуру;

не переписывай его только ради того, чтобы сделать код «новее».

Используй существующее рабочее решение.

---

# ВАЖНО: НЕ ДЕЛАТЬ ПОЛОВИНЧАТЫЕ МИГРАЦИИ

Не оставлять одновременно:

- старую и новую auth-систему;
- две системы UI;
- несколько вариантов API;
- старый и новый state management;
- несколько competing design systems;

если для этого нет временной migration-причины.

Если временно нужны две реализации — в MASTER PLAN обязательно должна быть отдельная задача по удалению старой после завершения migration.
